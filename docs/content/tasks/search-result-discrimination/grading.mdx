# How it is graded

Four measures, and only one of them consults a model.

| Measure | Who decides | Why |
| --- | --- | --- |
| nDCG@10, precision, recall, F1 | arithmetic | a function of the parsed reply and human labels |
| Abstention and fabrication | arithmetic | `relevant: []` is a boolean |
| Answer correctness | arithmetic | lenient string match against the gold answer |
| **Groundedness** | **a decision model** | no string match can tell whether a claim rests on the cited passage |

Keeping the model out of the first three is not fastidiousness. A judge is an
instrument that can change its mind between releases, and a benchmark whose
headline number moves when a third-party model is updated is measuring two
things at once.

## The shape the model must return

```json
{
  "ranking": ["3", "4", "1", "5", "2"],
  "relevant": ["3", "4"],
  "answer": "Notre Dame Fighting Irish football"
}
```

`relevant` and `answer` are required; `ranking` is optional, and scoring falls
back to the order of `relevant` when it is absent — a model that names its
evidence without ranking the noise has still answered.

`relevant: []` is not a failure to answer. It is the assertion *these results
do not answer the question*, and it is the right answer on all 40
[`no_answer`](./categories#no_answer--40-items) items.

### Parsing is deliberately lenient

The task measures whether a model can tell evidence from noise, not whether it
can follow a formatting instruction. So the parser accepts prose around the
JSON, a fenced code block, integer ids, and `[3]` for `3`. Everything it had to
repair is counted and published — `unknown-candidate`, `duplicate`,
`missing-field` — so the leniency is visible rather than free.

A reply with no JSON at all is recorded as **unparsed** and dropped from the
scored set, not scored as zero. The first task learned that lesson the hard
way: counting a silent reply as a decision put a model that failed every single
item into mid-table.

## Schema enforcement, where the provider offers it

Some providers will enforce a JSON Schema on the reply (`structured_outputs`);
others only promise valid JSON (`response_format`); others promise nothing. As
of 2026-09-23, across the 41 catalogued models OpenRouter serves:

| What the provider enforces | Models |
| --- | ---: |
| A JSON Schema (`structured_outputs`) | 34 |
| JSON, but no schema | 4 |
| Nothing | 3 |

The seven without schema enforcement:

| Model | JSON mode | Note |
| --- | :---: | --- |
| `deepseek/deepseek-r1` | yes | reasoning model |
| `qwen/qwen3-235b-a22b-thinking-2507` | yes | reasoning model |
| `qwen/qwen3-30b-a3b-thinking-2507` | yes | reasoning model |
| `qwen/qwen3-8b` | yes | |
| `meituan/longcat-2.0` | no | |
| `thinkingmachines/inkling` | no | |
| `thinkingmachines/inkling-small` | no | |

Three of the four strictest exclusions are reasoning models, which is the
awkward part: constrained decoding and a long thinking pass do not sit well
together at several providers.

This is recorded in `data/model_capabilities.json` with the date it was
checked, and regenerated by `uv run python scripts/model_capabilities.py` —
a provider fact that moves, pinned the same way prices are.

:::warning[Enforcing a schema is itself a confound]

Turning on strict mode for 34 models and leaving 7 on prompted JSON would make
the comparison partly about which provider ships which feature. So the harness
asks every model the same way, parses leniently, and records which path each
run took — the same treatment the first task gives native versus prompted tool
calling. Format compliance is reported separately, never folded into accuracy.

:::

## The judge: Jev, a decision model

Groundedness asks whether the claims in an answer appear in the candidates the
model cited. A judge is needed — and a judge that can simply assert "yes,
supported" is worth nothing.

The default judge is **[Jev](https://docs.typesafe.ai/)**, TypeSafe AI's
decision model, pinned at `jev-1.13.0`. It is not a chat model: it takes a
block of text and a set of typed questions, and returns an answer per question
with a probability. A "noul" is a yes/no question whose answer is P(true).

It is the right shape for this job for one reason above the rest: **it cannot
write text**. The harness supplies the passages, Jev votes on them, and there
is no span for it to invent. A generative judge has to be *made* honest; Jev is
never given the chance. Its only failure mode is a wrong vote, which is exactly
what the κ audit below measures.

```json
POST https://api.typesafe.ai/v1/systemone
{
  "model": "jev-1.13.0",
  "state": "QUESTION…\n\nANSWER GIVEN…\n\nRESULT [3]…\n\nRESULT [4]…",
  "questions": {
    "supported_by_3": {"type": "noul", "instructions": "Is every factual claim in the ANSWER GIVEN stated in RESULT [3]?"},
    "supported_by_4": {"type": "noul", "instructions": "…"},
    "supported_anywhere": {"type": "noul", "instructions": "…"}
  }
}
```

One question per cited result, so a wrong vote can be traced to the passage
that caused it, plus one about the answer overall. Every question is answered
in a single parallel pass, so an item costs one request.

Probabilities become verdicts with an explicit band of *not sure*:

| P(supported) | Verdict |
| --- | --- |
| ≥ 0.65 | `correct` |
| ≤ 0.35 | `incorrect` |
| between | `unjudgeable` |

The middle band is the model reporting that it does not know. Rounding it to a
side would invent confidence nobody has, and the existing `unjudgeable` cap of
2% of a release applies to it.

`jev-1.13.0` rather than `jev-latest`: a published number cannot come from a
model that moves underneath it, the same reason every dataset file carries a
checksum.

**Availability.** Jev is not in OpenRouter's model catalogue — I checked, zero
matches — so it is called directly at `api.typesafe.ai` with `TYPESAFE_API_KEY`,
the same arrangement as Moonshot and Avey. Third-party write-ups put it at
about $0.042 per million input tokens with output tokens free and 70–500 ms
latency; TypeSafe's own pricing page 404s, so treat those figures as reported
rather than verified. On 120 items it is small change either way.

## The generative judge, kept for the audit

The quote-carrying judge is still here, for the sample a human reads: a
probability says *how sure*, but not *why*, and an auditor wants the sentence.
That judge is made honest a different way — a verdict has to carry its
evidence:

```json
{"verdicts": [
  {"claim": "Don Criqui is from Buffalo, New York",
   "verdict": "correct",
   "candidate_id": "4",
   "quote": "Don Criqui (born May 5, 1940, Buffalo, New York)",
   "reasoning": "stated directly in the cited candidate"}
]}
```

The harness then looks for `quote` inside candidate `4`. If it is not there,
**the verdict is discarded** — not overridden, not downweighted, discarded. The
judge cannot assert support that does not exist, because the assertion has to
survive a string search.

Matching is whitespace- and accent-insensitive and nothing looser. A judge that
normalises a dash has still copied faithfully; a judge that paraphrases has not.

Either judge is restricted the same way.

### What the judge is not allowed to touch

- **Relevance.** TREC assessors graded these candidates. A model overruling
  them would quietly replace human ground truth with machine ground truth.
- **Answer correctness.** That is a string match against the gold answer. A
  judge there would make the judge part of the score.
- **Candidates the model did not cite.** The prompt shows only the cited ones.
  A judge given all twenty could find support in a passage the model never
  used, and score a lucky answer as a grounded one.

### Every verdict is pinned

`JudgeRun` carries the judge model, its kind (`typed` or `quoted`) and a
`prompt_version` (`grounded-noul-1` for Jev, `groundedness-1` for the
generative judge).
Change the wording, bump the version — old verdicts then cannot be silently
compared with new ones. Same reasoning as `priced_on` on a model's prices.

An answer with no usable verdict scores **None**, not "grounded". No evidence
is not a pass.

## Two numbers that will be published about the judge itself

1. **Discarded verdicts** — how often the generative judge quoted something
   that was not there. That is its own fabrication rate, measured rather than
   assumed. Jev has no equivalent, because it never quotes: its analogue is the
   share of answers that land in the `unjudgeable` band.
2. **Agreement with a human on a 30-item sample**, as Cohen's κ. Until that
   number exists, the judge is an unvalidated instrument and the groundedness
   column should be read as provisional.

## What is not built yet

The scoring, the judge prompt and the verification are written and tested
(`llmsearchbench.scoring.discrimination`, `llmsearchbench.scoring.judging`).
The Jev client is written too (`llmsearchbench.harness.typesafe`). What does
not exist yet is the harness that puts the task to models, the loop that walks
the judge over a run's answers, and the leaderboard. No model has been run
against this task, and no key for TypeSafe is configured.
